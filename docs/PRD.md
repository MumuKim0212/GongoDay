> 서비스명 **오늘공고** 확정.
>
> **읽는 법을 랜딩에 못 박는다** — "오늘 올라온 공고"가 아니라 **"오늘, 내가 신청할 수 있는 공고"** 다.
> 이 서비스는 §1에서 "새로 나온 것을 알려주는" 모델을 명시적으로 버렸으므로, 이름이 그쪽으로 읽히면
> 무엇을 하는 서비스인지가 흐려진다. 랜딩 한 문장(F-32)이 이 해석을 고정하는 역할을 겸한다.

## 1. 배경과 목적

출발점은 n8n으로 만든 **AI 지원사업 알리미**였다. 매일 새 공고를 알림으로 받았는데 두 가지가 걸렸다.

1. **필요 없는 공고가 대부분이었다.** 알림은 "새로 나온 것"을 기준으로 오지 받는 사람의 조건을 모른다.
2. **정책이 흩어져 있었다.** AI 지원사업은 정부24에, 청년·주거 정책은 온통청년에 있다.

그래서 방향을 뒤집었다. **알림을 받는 게 아니라, 내 조건을 한 번 등록해두고 여러 출처의 정책을 한 곳에서 걸러 보는 것**이다. 판정 기준은 정책 분야가 아니라 **"내가 해당되는가"** 하나다.

### 1.1 왜 웹인가 (REQ-01)

앞서 n8n으로 만든 알리미와 소재가 겹친다. 요구사항은 이 경우 **"웹이기 때문에 가능해진 것"** 을 요구한다.

| 웹이라서 가능해진 것 | n8n 알림/봇으로는 안 되던 이유 |
|---|---|
| **개인 조건을 저장해두고 판정에 쓴다** | 봇 대화로 나이·소득·거주지·상황을 매번 주고받는 건 비현실적 |
| **UI로 보고 조작한다** | 알림은 한 번에 한 줄씩 흘러간다. 목록을 훑고, 접고 펴고, 정렬을 바꾸고, 되돌아가 다시 보는 조작이 대화창에는 없다 |
| **복잡한 조건 조합을 한 번에 건다** | "서울 동대문구 + 주거 + 내 나이 + 1인가구"를 봇에게 시키려면 조건을 하나씩 주고받아야 하고, 조합이 늘수록 실패한다 |
| **판정 결과를 눌러서 원문까지 파고든다** | 메시지 한 줄로는 왜 그렇게 판정됐는지 확인할 수 없다 |

첫 번째가 핵심이다. **AI 판정의 입력이 되는 개인 프로필은 웹에서만 실용적으로 관리된다.**

> **알림을 다시 넣었다 (기능 4 · [ARCHITECTURE §11](ARCHITECTURE.md)).** 처음엔 "알림 모델 자체가 문제"라며 비목표로 뺐는데, n8n 알리미가 문제였던 지점은 정확히는 알림 자체가 아니라 **누가 받을지 모르고 모두에게 같은 것을 뿌리는 것**이었다. 이 서비스는 조건을 먼저 등록해두고(§5의 웹 흐름), 그 조건으로 판정한 것 중 **본인이 고른 점수 이상만, 원하는 사람만(opt-in)** 텔레그램으로 보낸다 — n8n의 "새로 나온 것 전부"와 다르다. 웹이 조건 관리를 맡고 알림은 그 결과를 미는 통로일 뿐이라, §1.1의 결론(개인 프로필은 웹에서 관리한다)은 그대로 남는다.

### 1.2 왜 좁히는가 — 선행 서비스가 이미 있다

**웰로(Wello)** 가 이 영역에서 더 넓은 범위를 이미 커버한다. 그런데 앱 후기에 이런 게 있었다.

> "지원도 못하고 관심도 없는 공고가 보인다"

**이 한 줄은 서로 다른 두 개의 불만이다.**

| 불만 | 정체 | 이 서비스의 대응 |
|---|---|---|
| **지원도 못하고** | 자격이 안 되는데 목록에 있다 | 코드 게이트 + AI 판정 + **인용 검증** (§7) |
| **관심도 없는** | 자격은 되지만 내 관심사가 아니다 | **분야 기본값을 좁게** 두고 사용자가 넓힌다 (§6.1) |

두 번째는 자격 판정으로 절대 안 풀린다. 40대 무주택자에게 육아 지원금은 "자격은 되는데 관심 없는" 공고다.

**그리고 범위를 좁히는 진짜 이유는 따로 있다.**

```
범위가 넓다 → 모든 사용자에게 공통으로 물을 수 있는 것만 프로필에 넣게 된다
           → 프로필이 얕아진다
           → 얕은 프로필로는 얕게밖에 못 거른다
```

전 국민 × 전 분야를 다루면 "당신 구·군이 어디입니까"를 물어도 쓸 데가 없다. **좁힌 만큼 깊게 묻는 것이 특화의 실체다.** 좁히기만 하고 프로필을 그대로 두면 그냥 작은 웰로가 된다.

### 1.3 무엇으로 좁혔나 — 실측으로 정했다

두 API를 전량/표본 호출해 **어느 축이 실제로 걷어내는지 셌다.**

| 축 | 온통청년 2,698건 | 정부24 10,964건 |
|---|---|---|
| 나이 (28세) | **4.0% 제거** ← 거의 못 거름 | 19.6% 제거 |
| **지역 (서울)** | **82.3% 제거** → 478건 | **68.3% 제거**(수도권 기준) |
| 코드 게이트 전체 | — | 64.5% 제거 |

**지역이 압도적이다.** 온통청년은 이미 전량 청년정책이라 나이로는 4%밖에 못 거른다. 그래서 **주축은 지역**이다.

→ 근거: 온통청년_실제응답검증.md §7 · 정부24_실제응답검증.md §5 (검증 기록 원본은 제출 과정에서 정리되어 저장소에는 없음)

### 1.4 수도권으로 좁혀서 얻는 것 — 시군구 단위 판정

지역으로 좁히면 **버리는 것 대비 얻는 것**이 있어야 한다. 있다.

- **정부24 `소관기관명`이 `"서울특별시 동대문구"` 형태로 온다.** 시도명으로 시작하는 비율 99.1%
- 행정구역이 재편된 데이터(인천 영종구·제물포구, 전남광주통합특별시)라 **외부 코드표로는 못 맞추고 데이터에서 도출해야 한다.** 전국 261개는 부담이지만 **수도권 3개 시도면 확정 가능하다**
- 시도명 정규화도 3개만 맞추면 된다

**"동대문구 사는 사람에게 동대문구 정책을 보여준다"** — 이건 시도 단위 서비스가 못 하는 세밀도다.

## 2. 목표 (Goals)

- 프로필을 한 번 입력하면, 목록에서 **각 정책에 해당되는지가 배지로 보인다**
- **출처가 다른 정책(온통청년·정부24)이 한 목록에 섞여 나온다** — 사용자는 어느 사이트에 있는지 몰라도 된다
- **거주 시·군·구까지 반영해 판정한다**
- 판정에는 **원문에서 그대로 인용한 근거 문장**이 붙는다
- **첫 화면이 훑어볼 만한 규모로 뜬다** — 분야 기본값을 좁게 두고 사용자가 넓힌다
- 정책 데이터가 Supabase에 누적되어, 수집 API가 실패해도 화면은 정상 동작한다
- 가입 절차 없이 판정을 받아볼 수 있다

## 3. 비목표 (Non-goals)

| 비목표 | 이유 |
|---|---|
| **비수도권 지역** | 특화 축이다(§1.3). 데이터는 전량 수집해 두므로 나중에 여는 것은 필터 조건 변경이다 |
| **법안 추적** | 원 기획서에 있었으나 뺀다. **지금 내게 필요한 것이 아니다.** 법안은 신청 대상이 아니라 "내가 해당되는가"라는 이 서비스의 질문이 성립하지 않는다 |
| 신청 대행 · 서류 준비 안내 | 최종 확인은 원문으로 넘긴다 |
| 마감 임박 필터 · 신청기간 파싱 | 두 소스 모두 포맷이 제각각이고 빈 값이 많다 (§8 R2) |
| **온통청년의 시군구 단위 판정** | 실익이 없다. 서울 정책 478건 중 동대문구 코드를 가진 것이 467건 — **2%밖에 안 줄어든다.** 온통청년은 시도 단위까지만 (§7.3) |
| 기업마당 등 3번째 소스 | 구조는 열려 있다 (§9) |
| 정책 추천 알고리즘 | 판정만 한다. 순위를 매기지 않는다 |
| 이메일 회원가입 | **MVP 범위에서만 뺀다.** 익명 세션으로 대체하고(§6.5), 조건 입력에 로그인을 요구할 때 다시 넣는다 — 그때 R4가 함께 풀린다 (§9.5) |

## 4. 타겟 사용자

- **대상**: **수도권(서울·인천·경기) 거주 개인**으로, 정부 지원정책을 한 번이라도 찾아본 사람. 관심 분야가 하나가 아닌 사람
- **지금 겪는 불편**
  - 정책이 사이트별로 흩어져 있어 여러 곳을 돌아야 한다
  - 목록에서는 해당 여부를 알 수 없어, 원문을 하나씩 열어 자격요건 문단을 읽어야 한다
  - 넓게 훑어주는 서비스는 자기와 무관한 공고까지 같이 보여준다 (§1.2)
- **이 서비스를 쓰면**: 조건을 한 번 입력해두면 여러 출처의 정책이 **내 구·군 기준으로** 걸러진다. 왜 그렇게 판정됐는지도 원문 인용으로 확인할 수 있다

## 5. 핵심 사용자 흐름

```
[첫 방문] 정책 목록이 이미 채워져 있음 (수도권 + 기본 분야)
    │
    ▼
"내 조건 입력하기" → 생년 / 시도·시군구 / 소득 / 개인상황 / 가구상황 / 사업자상황
    │                 + 관심 분야 (기본 2개 켜짐)
    ▼
목록으로 복귀 → 코드 조건 + 분야로 1차 축소 (수백 건 규모)
    │
    ▼
목록을 열면 자동 AI 판정 → 5단계 점수 배지
    │
    ▼
정책 클릭 → 상세: 원문 + 판정 근거 인용 + 원문 링크 + 스크랩
```

**중요**: `아님`으로 판정된 정책도 목록에서 사라지지 않는다. 배지만 붙고 접힌 상태로 남는다 (§7.5).

## 6. 기능 요구사항

### 6.1 기능 1 :: 정책 목록 · 검색

| ID | 요구사항 |
|---|---|
| F-01 | 수집된 정책 목록을 최신순으로 표시 (페이지당 10건). **온통청년·정부24가 한 목록에 섞인다** |
| F-01a | **기본 필터: 수도권 + 프로필 코드 조건(나이·지역) + 기본 분야** |
| ~~F-01b~~ | ~~**"전체 보기" 토글**~~ — **뺐다.** 필터를 풀고 싶으면 걸어둔 필터를 끄면 되고, 조건과 무관한 전체 목록을 찾는 사용자는 없다. 다만 **나이·지역은 프로필을 지워야만 풀린다**는 것이 남는다 (§7.5) |
| F-02 | 정책명 키워드 검색 |
| **F-03** | **분야 필터. 기본값은 `일자리·창업` + `주거` 두 개만 켜진 상태**이고, 나머지는 사용자가 켠다 |
| F-03a | 출처 필터 (전체 / 온통청년 / 정부24). 카드에도 출처 배지 |
| F-04 | 수집 데이터가 0건이어도 화면이 깨지지 않고 안내 문구 표시 |
| F-05 | "갱신" 버튼으로 수집을 수동 트리거 (소스별 마지막 수집 시각 표시) |

| 통합 분야 | 온통청년 `lclsfNm` | 정부24 `서비스분야` | 기본 |
|---|---|---|---|
| **일자리·창업** | 일자리 | 고용·창업 | **ON** |
| **주거** | 주거 | 주거·자립 | **ON** |
| 교육·훈련 | 교육 / 교육･직업훈련 | 보육·교육 | off |
| 복지·금융·문화 | 복지문화 / 금융･복지･문화 | 생활안정 / 문화·환경 / 보호·돌봄 | off |
| 참여·권리 | 참여권리 / 참여･기반 | 행정·안전 | off |
| 건강·의료 | — | 보건·의료 | off |
| 임신·출산 | — | 임신·출산 | off |
| 농림축산어업 | — | 농림축산어업 | off |

> 온통청년 `lclsfNm`에 **신·구 분류가 섞여 있다** (`복지문화`↔`금융･복지･문화` 등). 정규화하지 않으면 같은 분야가 선택지에 두 번 나온다 (검증기록 §7.5).

### 6.2 기능 2 :: AI 해당 판정 ★ 핵심

| ID | 요구사항 |
|---|---|
| F-10 | 프로필 입력 폼 (생년 / 성별 / **시도 + 시군구** / 소득구간 / 개인상황 / 가구상황 / 사업자상황 / 관심분야) |
| F-11 | 목록을 열면 현재 페이지 정책을 **자동으로** 판정. 판정을 못 받은 건만 `N건 다시 판정` |
| F-11a | **코드 게이트**: 코드로 대조 가능한 조건이 불일치면 AI 호출 없이 `아님` 확정 (§7.2) |
| F-11b | 판정 근거가 코드인지 AI인지 화면에 구분해 표시 |
| F-12 | 판정 결과를 **5단계 점수 배지**로 표시. `해당/애매/아님` 셋으로는 `애매`가 한 덩어리라 사용자가 무엇을 할 수 있는지 갈리지 않았다 — 확인 항목 수로 쪼갠다 ([ARCHITECTURE §5.6](ARCHITECTURE.md)) |
| F-13 | 판정 근거를 **원문에서 인용한 문장**으로 표시 |

## 7. AI 설계

### 7.1 소스가 둘이어도 판정 로직은 하나다

두 소스는 자격요건을 서로 다른 형태로 준다. **수집 단계에서 차이를 흡수한다.**

| 조건 | 온통청년 | 정부24 |
|---|---|---|
| 나이 | `sprtTrgtMinAge` / `MaxAge` (72.7% 채움) | `JA0110` / `JA0111` (67.8%) |
| 지역 | `zipCd` 5자리 다중 → **시도 단위** | `소관기관명` 문자열 → **시군구 단위** |
| 성별 | 없음 | `JA0101` / `JA0102` |
| 소득 · 상황 · 가구 · 사업자 | 코드 의미 불명 → 미사용 (§8 R6) | `JA02xx` / `JA03xx` / `JA04xx` / `JA11xx` |
| 자유 텍스트 | `plcyExplnCn`·`plcySprtCn` 100%, `addAplyQlfcCndCn` 33.7% | `지원대상`·`지원내용` 100%, `선정기준` 99.8% |

게이트·프롬프트·검증은 소스를 모른다. 소스별 분기는 `lib/sources/*.ts` 안에서 끝난다.

> **정부24를 넣으면 코드 게이트가 강해진다.** 온통청년은 나이·지역 2개만 코드로 대조할 수 있는데 정부24는 7개를 준다. 소스 추가가 판정 품질을 올리는 방향으로 작용한다.

### 7.2 판정은 2단이다 — 코드로 확정, 텍스트만 AI

```
1단 :: 코드 게이트 (결정론적, AI 호출 전)
      ├─ 조건 불일치 → '아님' 확정. AI를 호출하지 않는다
      │                 근거: "이 정책은 19~39세, 입력하신 나이는 45세"
      └─ 통과 → 2단
                  │
2단 :: AI 판정 (텍스트로만 표현된 조건)
      └─ '해당' / '애매' / '아님' + 원문 인용 근거
```

얻는 것이 셋이다.

1. **코드로 답이 나오는 조건은 AI가 틀릴 수 없다** — 계산이니까
2. **AI 호출이 줄어든다** — 게이트에서 걸러진 정책은 호출하지 않는다
3. **근거가 검증 가능한 사실이 된다** — "AI가 그렇게 말했다"가 아니라 "정책은 19~39세, 당신은 45세"

> Day04 사주에서 쓴 구조와 같다 — **계산은 코드, 해석은 AI.**

**게이트는 "모르면 통과"다.** 정책에 조건 코드가 없거나 프로필이 비어 있으면 **검사를 건너뛴다.** 게이트가 하는 일은 "확실히 아닌 것을 빼는 것"이지 "확실한 것만 남기는 것"이 아니다.

**나이 경계는 ±1년 여유를 둔다.** 문구가 만나이인지 연나이인지 제각각이라 경계에서 오판할 수 있다. **경계에서 틀려 신청 기회를 잃게 만드는 것보다 애매하다고 말하는 게 낫다.**

**`sprtTrgtAgeLmtYn`은 쓰지 않는다.** 값이 `N`인데 원문에 "19세~39세"가 명시된 건이 있었다.

### 7.3 지역 판정 — 소스마다 세밀도가 다르다

| 소스 | 세밀도 | 근거 |
|---|---|---|
| 온통청년 | **시도** | 시군구까지 가도 478→467건, **2%밖에 안 줄어든다.** 대부분의 서울 정책이 서울 전역 대상 |
| 정부24 | **시군구** | 소관기관의 65.1%가 시군구. 동대문구 정책이 표본에서만 73건 |

**전국 정책 판별**

- 온통청년: `zipCd`를 비우는 게 아니라 **256개 코드를 전부 나열한다.** 시도 prefix가 15개 이상이면 전국 (416건, 15.4%)
- 정부24: `소관기관유형 = 중앙행정기관` (1,053건)

**프로필에서 시군구를 안 고르면 시도 단위로만 판정한다.** 구 단위 정책도 통과시킨다 — 숨기지 않는다.

### 7.4 AI가 이상한 답을 줬을 때 (제출 문서 §4에 그대로 들어갈 내용)

3단으로 막는다.

| 단계 | 검사 | 실패 시 |
|---|---|---|
| 1 | `verdict`가 정의된 3개 값 중 하나인가 | 판정 폐기 → `unclear` |
| 2 | **`quote`가 원문에 문자 그대로 있는가** (공백 정규화 후 부분문자열) | 판정 폐기 → `unclear` + "근거를 원문에서 찾지 못했습니다" |
| 3 | 호출 실패 / 타임아웃 / JSON 파싱 실패 | `unclear` (화면은 정상 동작) |

**2번이 핵심 방어다.** AI가 자격 요건을 지어내면 그 문장은 원문에 없다. 문자열 대조만으로 잡힌다.

1단계는 Gemini 구조화 출력(`responseSchema`)으로 대부분 사전 차단되지만 **검증은 그대로 둔다.** 모델이 스키마를 지킨다는 보장을 서버가 신뢰하지 않는다.

> Foodprint에서 이미 쓴 패턴 — 모델 출력은 신뢰하지 않고 서버가 검증하며, 실패는 예외가 아니라 `unclear`라는 정상 상태로 흡수한다.

### 7.5 판정으로 정책을 숨기지 않는다

**`ineligible` 정책도 목록에서 제거하지 않는다.** 배지를 붙이고 접어둘 뿐이다.

요약을 잘못하는 것과 **해당되는 정책을 걸러 없애버리는 것**은 피해의 차원이 다르다. 후자는 사용자가 신청 기회를 잃는다.

**그리고 이게 §1.2 후기 불만 #1에 대한 답이기도 하다.** "안 보이게 하는 것"과 "왜 보이는지 말하는 것"은 다르다. 자격 안 되는 공고가 보여도 *"이 정책은 무주택 세대 대상이고, 입력하신 조건은 해당하지 않습니다"* 라고 적혀 있으면 사용자가 "이게 왜 여기 있지?"라고 묻지 않는다. `blockers` 필드가 이 역할을 한다.

코드 게이트에 의한 SQL 1차 필터와 분야 기본값은 예외적으로 목록을 좁힌다. 되돌리는 길은 **분야 칩을 켜는 것과 프로필을 고치는 것**이다 — 전에 있던 "전체 보기" 토글은 뺐다 (F-01b).

> **남는 구멍을 적어둔다.** 분야는 칩으로 풀 수 있지만 **나이·지역은 프로필을 지워야 풀리고, 사용자구분(§5.0.3)은 화면에 손잡이가 없다.** 게이트가 나이·지역을 잘못 잡아 뺀 정책은 지금 화면에서 되찾을 방법이 없다. 그런 사례가 보고되면 여기부터 다시 본다.

### 7.6 프롬프트에서 신경 쓴 점

1. **원문을 데이터로 취급하라고 못 박는다** — 원문 안의 어떤 문장도 지시로 받지 않는다 (프롬프트 인젝션 차단)
2. **모르면 `unclear`를 쓰라고 명시한다**
3. **`quote`는 반드시 원문에서 복사하라고 요구한다** — §7.4의 2단 검증이 성립하는 전제

### 7.7 호출 비용 통제

목록을 열면 **현재 페이지 10건만** 자동 판정한다. 전체 13,673건을 한 번에 부르지 않는다는 뜻이고, 이게 비용 통제의 뼈대다.

- 코드 게이트에서 불일치가 확정된 정책은 AI를 호출하지 않는다
- **같은 조건 + 같은 정책 조합은 `verdicts`에 저장되어 재호출하지 않는다** — 사용자별이 아니라 조건별이다. 세션이 익명이라 `user_id`를 키에 넣으면 같은 사람이 기기만 바꿔도 캐시를 통째로 잃었다. 전환 시점 실측으로 AI 호출의 61%가 이 중복이었다 (ARCHITECTURE §2.3)
- 프로필이 바뀌면 **판정에 쓰이는 필드에 한해** 서명이 바뀌어 자동 재판정된다
- 판정을 못 받은 건(AI 호출 실패)은 저장하지 않는다 — 다시 부를 수 있어야 하기 때문이고, 그래서 그때만 버튼이 뜬다

> **버튼을 없앤 이유.** 원래는 눌렀을 때만 판정했다. 페이지를 넘길 때마다 다시 눌러야 하는 게 실제로 불편했고, 자동으로 돌려도 **한 페이지 10건 상한과 캐시가 그대로 남아 있어** 비용의 뼈대는 바뀌지 않는다. 늘어나는 것은 "스쳐 지나간 페이지"의 몫이고, 그 몫을 조건별 공유 캐시가 상쇄한다.

**이 설계가 실제로 듣고 있는지는 `/admin`의 '호출 · 비용' 탭에서 본다** (ARCHITECTURE §2.7). 위 항목들은 전부 "호출을 줄인다"는 주장인데, 배포본에서 그게 사실인지 확인할 방법이 오래 없었다 — `verdicts` 테이블에는 **캐시로 막은 몫도, 실패한 호출도, 재판정도 남지 않기 때문이다.** 배치마다 장부(`verdict_runs`)를 한 줄씩 적어 캐시 적중률·실제 호출 수·토큰을 되읽는다.

> **비용은 호출 수가 아니라 토큰으로 매겨진다.** 그래서 장부에 토큰을 같이 적는다. 단가는 코드에 지어 넣지 않는다 — 토큰은 API가 준 사실이지만 단가는 아니고, **틀린 단가로 계산한 금액은 사실인 척하는 거짓말이다.** 상수 하나(`PRICE_PER_1M`)를 비워 두고, 채우기 전에는 화면이 금액 대신 토큰만 보여준다.

**유저당 사용량 제한은 아직 넣지 않았다.** 장부에 `(requested_by, created_at)` 인덱스를 걸어 "이 사용자가 최근 N시간에 몇 번 호출했나"를 싸게 물을 수 있게만 해 뒀다. 제한을 건다면 **익명이 아니라 로그인 계정 기준**이어야 한다 — 익명 uid는 시크릿 창 하나로 새로 만들어지므로 제한이 성립하지 않는다 (§9.5).

| R4 | 익명 세션이라 브라우저 데이터 삭제 시 프로필·스크랩 유실. 기기가 바뀌어도 따라오지 않는다 | **MVP에서는 허용한다** (제출 문서에 명시). **로그인을 넣으면 풀리는 문제다** — 같은 uid에 식별 정보를 붙이는 것이라 스키마·RLS는 그대로다 (§9.5) |
| R5 | 서버리스 실행시간 제한 | 소스별 `last_page` 이어받기 + `maxDuration` 명시. **온통청년 수집 중 HTTP 500이 1회 발생했다 → 지수 백오프 재시도 필수** |

## 9. 확장 설계 — 나중에 열 것

### 9.1 비수도권은 필터 조건 변경으로 열린다

**데이터는 전량 수집한다.** 수도권 특화는 화면 필터의 기본값이지 수집 범위가 아니다. 지역을 넓히는 것은 필터 해제이고, 그때 필요한 건 **비수도권 시군구 목록 도출**뿐이다.

### 9.2 테이블을 소스별로 쪼개지 않는다

`policies` 하나에 `source` 컬럼과 `unique (source, external_id)`. 소스 추가는 행 추가다. 응답 원본은 `raw jsonb`에 통째로 보관한다.

### 9.3 프로필은 정부24 코드 체계를 기준으로 삼는다

정부24 `supportConditions`가 **명세에 코드표가 딸린** 유일한 구조화 코드다. 이걸 프로필의 기준 체계로 쓴다.

| 정부24 코드 | 의미 | 프로필 필드 |
|---|---|---|
| JA0101 / JA0102 | 남성 / 여성 | `gender` |
| JA0110 / JA0111 | 대상연령 시작/종료 | `birth_year` |
| JA0201~JA0205 | 중위소득 구간 | `income_bracket` |
| JA0301~JA0330 | 임산부 / 대학생 / 근로자 / 구직자 / 장애인 … | `situations[]` |
| JA0401~JA0414 | 다문화 / 1인가구 / 무주택세대 / 다자녀 … | `household[]` |
| JA1101~JA1103 | 예비창업자 / 영업중 / 폐업예정 | `business_status` |

**`business_status`를 넣는 이유**: 이 프로젝트의 출발점이 AI 지원사업이고 그 대다수가 창업·사업자 대상이다. 다만 `JA11xx` 채움률이 6.2%라 **창업 판정은 코드보다 `지원대상` 텍스트에 의존하게 된다** — AI 판정의 몫이다.

### 9.4 지금 만들지 않는 것

**소스 어댑터 인터페이스를 만들지 않는다.** `youth.ts`와 `gov24.ts`가 같은 시그니처를 갖되 공통 타입으로 묶지 않는다. 두 개는 아직 추상화를 뽑을 표본이 아니다.

### 9.5 계정 로그인 — 익명 세션은 MVP의 임시 방편이다

지금은 첫 방문에 `proxy.ts`가 `signInAnonymously()`로 익명 세션을 만든다 (F-30, [ARCHITECTURE §1.1](ARCHITECTURE.md)). **MVP에서는 이게 맞다** — 조건을 넣기 전에 회원가입 폼이 서면 "내가 신청할 수 있는 공고"를 보기도 전에 이탈한다.

대가는 **세션이 쿠키 하나에 묶인다**는 것이다. 쿠키를 지우거나 다른 기기·시크릿 창에서 열면 새 익명 사용자가 되고 프로필·스크랩·판정이 따라오지 않는다 (§8 R4).

**로그인을 넣으면 그대로 풀린다.** `profiles`·`scraps`·`verdicts`가 이미 `auth.uid()`에 묶여 있고 RLS도 그 기준이라, 바뀌는 것은 **그 uid가 익명이냐 계정이냐뿐이다** — 스키마도 정책도 그대로다.

| 지금 | 로그인 이후 |
|---|---|
| 쿠키를 지우면 프로필·스크랩 유실 (R4) | 계정으로 복구된다 |
| 기기마다 다른 사용자 | 같은 조건·스크랩이 따라온다 |
| 조건 입력에 진입 장벽이 없다 | **조건 입력 시점에** 로그인을 요구한다 — 목록 열람은 그대로 열어둔다 |

**이행 경로** (Supabase 문서 확인): 익명 사용자는 **식별 정보를 붙이면 같은 uid 그대로 정식 사용자가 된다** — 이메일·전화는 `updateUser({ email })`, OAuth는 `linkIdentity({ provider })`. 대시보드에서 **Manual Linking**을 켜야 한다(베타). uid가 유지되므로 **익명으로 넣어둔 조건과 스크랩이 그대로 남는다** — 행을 옮기는 마이그레이션이 필요 없다.

> ⚠️ **예외 하나를 먼저 설계한다.** 익명 사용자를 **이미 있는 계정**에 붙이는 경우는 uid가 유지되지 않는다. 그 계정으로 로그인한 뒤 `profiles`·`scraps`·`verdicts`의 `user_id`를 옮겨야 하고, **양쪽에 조건이 다 있으면 어느 쪽을 남길지**를 정해야 한다. 로그인을 열 때 이 분기가 첫 번째 결정이다.

> 익명과 계정을 화면에서 구분해야 할 일이 생기면 JWT의 `is_anonymous` 클레임을 RLS에서 본다. 지금은 구분하지 않는다 — 익명 사용자도 정식 사용자와 같은 `authenticated` 역할이라 현재 정책이 그대로 동작한다.
