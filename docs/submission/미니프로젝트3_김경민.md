# 오늘공고

## 0. 기본 정보
- 이름 : 김경민
- 배포 주소 : https://gongoday.vercel.app
- 사용한 AI 모델/API : **Google Gemini API — `gemini-3.5-flash`** (구조화 출력 `responseSchema`, `temperature: 0`)
  - 후보 5개(2.5·3.5·3.6 세대 × flash·flash-lite)를 실제 정책 데이터로 비교해 정했습니다. 근거는 §4 마지막에 적었습니다.

## 1. 한 줄 소개
수도권에 사는 개인이 여러 곳에 흩어진 정부·지자체 지원정책 중 **내가 실제로 신청할 수 있는 것**만 골라 보도록, 조건을 한 번 등록해두면 AI가 원문 근거와 함께 해당 여부를 판정해주는 서비스입니다.

## 2. 이런 사람을 위해 만들었습니다
- **대상** : 수도권(서울·인천·경기)에 사는 개인으로, 지원정책을 한 번이라도 찾아본 사람. 관심 분야가 하나가 아닌 사람
- **그 사람이 지금 겪는 불편**
  - 정책이 사이트별로 흩어져 있습니다. AI·창업 지원사업은 정부24에, 청년·주거 정책은 온통청년에 있어 여러 곳을 돌아야 합니다
  - 목록만 봐서는 해당 여부를 알 수 없어, 공고를 하나씩 열어 자격요건 문단을 읽어야 합니다
  - 넓게 훑어주는 기존 서비스는 자격이 안 되거나 관심 없는 공고까지 같이 보여줍니다
- **이 서비스를 쓰면 달라지는 것**
  - 조건을 한 번 등록해두면 두 출처의 정책이 **한 목록에 섞여** 나오고, 어느 사이트에 있는지 몰라도 됩니다
  - 각 정책에 **해당 / 애매 / 아님** 배지가 붙고, **왜 그렇게 판정됐는지 원문에서 인용한 문장**이 함께 보입니다
  - 시·도가 아니라 **거주 구·군까지 반영해서** 걸러집니다

## 3. 주요 기능 (3개 이내)

**① 정책 목록 · 검색** — 온통청년과 정부24를 한 테이블에 모아 최신순으로 보여줍니다. 분야 필터는 기본값을 `일자리·창업`+`주거` 두 개만 켠 상태로 두고 사용자가 넓힙니다. 첫 화면이 수천 건이 되지 않게 하려는 것이고, 걸러진 것을 볼 수 있도록 **"전체 보기" 토글을 항상 남깁니다.**

**② AI 해당 판정 ★ 핵심** — "이 페이지 10건 판정하기"를 누르면 현재 페이지 정책을 한 번에 판정해 `해당 / 애매 / 아님` 배지를 붙이고, 판정이 끝나면 페이지 안에서 `해당 → 애매 → 아님` 순으로 다시 정렬합니다. 판정 근거는 **원문에서 그대로 인용한 문장**이고, 상세 화면에서 원문의 해당 구간이 하이라이트됩니다. 같은 조건으로 다시 눌러도 **AI 호출은 0건**입니다(저장된 판정을 재사용).

**③ 스크랩** — 상세 화면에서 스크랩해두고 목록의 "스크랩만 보기"로 모아 봅니다.

## 4. AI를 어디에 어떻게 썼나요

- **AI가 하는 일** : **코드로 대조할 수 없는 자유 텍스트 자격요건**을 사용자 조건과 대조해 `해당 / 애매 / 아님`을 판정하고, 그 근거가 되는 문장을 원문에서 인용합니다.

  판정을 2단으로 나눴습니다. **나이·지역·성별·소득 같은 코드로 답이 나오는 조건은 AI를 부르지 않고 코드가 확정합니다.** 계산이라 AI가 틀릴 수 없고, 근거도 "AI가 그렇게 말했다"가 아니라 *"이 정책은 19~39세, 입력하신 나이는 45세"* 라는 검증 가능한 사실이 됩니다. 대표 프로필(28세·서울) 기준으로 재보면, 1차 필터를 통과해 목록에 오르는 **617건 중 103건이 AI 호출 없이 코드로 확정**되고 514건만 AI로 넘어갑니다. **개인이 신청할 수 없는 `법인/시설/단체` 전용 271건은 그보다 앞에서 목록 SQL이 걸러냅니다** (§8 ④).

  게이트 원칙은 **"모르면 통과"** 입니다. 정책에 조건이 없거나 프로필이 비어 있으면 검사를 건너뜁니다. 게이트가 하는 일은 "확실히 아닌 것을 빼는 것"이지 "확실한 것만 남기는 것"이 아닙니다.

- **입력으로 무엇을 주고, 무엇을 받나요**
  - **입력** : 정책 원문을 라벨 붙여 조립한 텍스트(정책명 · 요약 · 소관기관 · 지원대상 · 선정기준 · 지원내용 · 소득조건 · 기타사항 · 신청기간) + 사용자 조건(나이 · 거주 시도/시군구 · 개인상황 · 가구상황 등)
  - **출력** : `{ verdict, reason, quote, blockers }` 구조화 JSON
  - 신청방법·구비서류는 **일부러 입력에서 뺐습니다.** 자격 판정과 무관한데 넣으면 토큰만 늘고, 무엇보다 **인용 검증 대상이 넓어져 엉뚱한 문장이 근거로 통과**합니다.

- **AI가 이상한 답을 줬을 때 어떻게 처리했나요** : 3단으로 막습니다.

  | 단계 | 검사 | 실패 시 |
  |---|---|---|
  | 1 | `verdict`가 정의된 3개 값 중 하나인가 | 판정 폐기 → `애매` |
  | 2 | **`quote`가 원문에 문자 그대로 있는가** (공백 정규화 후 부분문자열) | 판정 폐기 → `애매` + "근거를 원문에서 찾지 못했습니다" |
  | 3 | 호출 실패 / 타임아웃 / JSON 파싱 실패 | `애매` (화면은 정상 동작) |

  **2번이 핵심 방어입니다.** AI가 자격 요건을 지어내면 그 문장은 원문에 없으므로 문자열 대조만으로 잡힙니다. 1번은 Gemini 구조화 출력으로 대부분 사전 차단되지만 검증은 그대로 뒀습니다 — **모델이 스키마를 지킨다는 보장을 서버가 신뢰하지 않습니다.**

  그리고 실패를 예외가 아니라 **`애매`라는 정상 상태로 흡수**합니다. 한 건이 실패해도 다른 카드는 정상이고 화면이 비지 않습니다. 실제로 무효한 API 키로 서버를 띄워 강제로 실패시켜 봤는데, 코드로 확정된 카드는 그대로였고 AI로 넘어간 카드만 `애매`가 됐습니다. **호출 실패는 저장하지 않아서** 다시 누르면 재시도됩니다.

  > **그 결과 화면에서 가장 많이 보이는 배지는 `애매`입니다.** 30건 실측에서 `해당 1 · 애매 25 · 아님 4`였습니다. 원문에 근거가 없으면 지어내지 말라는 규칙의 직접적인 결과입니다. 자격요건을 "확인할 수 없다"고 말하는 것이 정확하지 않은 확신보다 낫다고 봤습니다 — 이 서비스에서 틀린 `해당`은 헛걸음이고, 틀린 `아님`은 신청 기회를 잃는 일입니다.

- **프롬프트에서 신경 쓴 점 1가지** : **"사용자가 고른 항목이 전부는 아니다"를 명시한 것**입니다.

  프로필의 개인상황·가구상황·사업자상황은 다중선택이라 사용자가 고른 것만 들어 있습니다. 이걸 말해주지 않으면 모델이 *"근로자를 골랐으니 사업자가 아니다"* 로 추론해 **사업자·창업 대상 정책을 전부 `아님` 처리**했습니다. 이 서비스의 출발점이 AI 지원사업(=대부분 창업·사업자 대상)이라 핵심 용도가 통째로 날아가는 구멍이었습니다.

  규칙을 보강하자 세 모델의 `아님` 판정이 **7·9·7건 → 4·4·4건**으로 수렴하고 모델 간 불일치도 **33% → 23.3%** 로 떨어졌습니다. **모델을 바꿔서 고친 게 아니라 프롬프트 구멍을 메워서 고친 문제**였습니다.

### 모델은 실측으로 골랐습니다

문서에 기본값으로 적어뒀던 `gemini-2.5-flash`를 그대로 쓰지 않고, 실제 정책 30건(두 출처 절반씩)에 **배포될 코드 그대로**(프롬프트·조립·검증 함수 동일) 5개 모델을 돌렸습니다.

| 모델 | 인용검증 통과 | 호출 실패 | 지연 p50/p95 | 결정론 |
|---|---|---|---|---|
| gemini-2.5-flash-lite | 86.7% | 0 | 1.2s / 1.7s | 100% |
| **gemini-2.5-flash** (원래 기본값) | **90.0%** | **타임아웃 1건** | **4.3s / 12.4s** | **80%** |
| gemini-3.5-flash-lite | 100% | 0 | 1.2s / 1.6s | 90% |
| **gemini-3.5-flash** ← 채택 | **100%** | **0** | **3.0s / 4.2s** | **100%** |
| gemini-3.6-flash | 100% | 0 | 4.1s / 7.7s | 90% |

**기본값으로 적어뒀던 모델이 가장 나빴습니다.** 2.5 세대는 인용을 그대로 복사하지 못합니다(86.7~90%). 인용 검증이 이 서비스가 AI를 신뢰하는 유일한 근거이므로 치명적입니다.

프롬프트를 보강한 뒤에는 3.x 세 모델이 인용검증·결정론 모두 100%로 동률이 되어, **남은 불일치 7건을 원문과 하나씩 대조해** 갈랐습니다 — flash-lite는 "청년 누구나"에 없는 조건을 덧붙이는 등 3건 오판, 3.6-flash는 2건(구직자 대상 사업을 `해당`, 소관기관 관할 규칙 무시), **3.5-flash는 0건**이었습니다.

> 마지막 판단은 정답 라벨이 아니라 원문을 읽고 내린 것이고 표본이 7건입니다. 객관 수치(인용검증·결정론·지연·실패)로는 셋이 동률이었고 그다음을 이 방법으로 갈랐다는 점을 밝혀둡니다.

## 5. 데이터 설계

- **테이블 이름과 역할**

  | 테이블 | 역할 |
  |---|---|
  | `policies` | 수집한 정책 13,662건 (온통청년 2,698 + 정부24 10,964). **출처 무관 공통 스키마** |
  | `profiles` | 사용자가 등록한 내 조건. 익명 세션 소유자 본인만 읽고 씁니다 |
  | `verdicts` | AI 판정 결과 **겸 캐시** |
  | `scraps` | 스크랩 |
  | `sync_runs` | 수집 실행 기록. 출처별 마지막 갱신 시각 표시 + 중단 시 이어받기 |

- **주요 컬럼**
  - `policies` : `source` / `external_id` (둘이 unique) · 판정용 텍스트를 **라벨별로 나눈 칸들** · `is_nationwide` · `region_sidos[]` · `region_sigungu` · `categories[]` · `audiences[]` · `age_min` / `age_max` · `eligibility_codes` (jsonb) · `raw` (응답 원본) · `source_registered_at` (정렬 기준)
  - `verdicts` : `profile_signature` · `verdict` · `decided_by` (코드/AI) · `quote` · `quote_verified` · `blockers[]`, `unique (policy_id, user_id, profile_signature)`

- **이렇게 설계한 이유**
  - **출처별로 테이블을 쪼개지 않았습니다.** `source` 컬럼 하나로 한 테이블에 담으면 출처 추가가 곧 행 추가이고, 목록·판정·검색 코드가 출처를 몰라도 됩니다. 두 API의 형태 차이는 **수집 단계에서 흡수**하고, 그 뒤로는 판정 로직이 출처를 모릅니다
  - **판정용 텍스트를 한 칸에 합치지 않고 라벨별로 나눴습니다.** 합치면 다시 못 나누고, 어느 칸이 비었는지 세어야 채움률을 알 수 있기 때문입니다
  - **`profile_signature`가 캐시 키입니다.** 프로필이 바뀌면 서명이 바뀌고 unique 제약이 새 행을 허용해 자동으로 재판정됩니다. 판정에 쓰이지 않는 필드(관심분야)는 서명에서 빼서 불필요한 재호출을 막았습니다. 서명은 **서버가 자기 쿼리로 다시 계산합니다** — 클라이언트가 보낸 값을 믿지 않습니다
  - **배열 컬럼은 전부 `not null default '{}'`** 입니다. nullable이면 배열 겹침 비교(`&&`)가 NULL을 반환해 **해당 행이 목록에서 통째로 사라집니다**
  - **RLS를 5개 테이블 전부에 걸었습니다.** `policies`·`sync_runs`는 읽기만 공개하고 **클라이언트 쓰기 정책을 아예 만들지 않았습니다.** 수집은 서버 전용 키로만 씁니다

## 6. 화면 흐름

1. **목록 화면에 들어옵니다.** 로그인 없이 익명 세션이 자동으로 만들어지고, 정책 목록이 이미 채워진 채로 보입니다. 상단 한 문장이 "오늘 올라온 공고"가 아니라 **"오늘, 내가 신청할 수 있는 공고"** 임을 알려주고 첫 동작을 안내합니다.
2. **"내 조건 입력하기"를 눌러 프로필을 채웁니다.** 생년 / 시도·시군구 / 소득 / 개인상황 / 가구상황 / 사업자상황 / 관심분야 — **전부 선택 사항**이고, 채울수록 정확해진다고 안내합니다. 저장하면 목록으로 돌아옵니다.
3. **"이 페이지 10건 판정하기"를 누릅니다.** 판정 중에는 배지 자리에 스켈레톤이 서고, 끝나면 `해당 / 애매 / 아님` 배지가 붙습니다. **코드로 확정된 것인지 AI 판정인지 배지에 구분해 표시**합니다.
4. **정책을 눌러 상세로 들어갑니다.** 판정 근거가 된 원문이 그대로 보이고 **인용 문장이 하이라이트**됩니다. 신청방법·구비서류는 **판정에 쓰이지 않은 정보**라 별도 블록으로 나눠 두었습니다. 원문 링크로 넘어가거나 스크랩할 수 있습니다.

**`아님`으로 판정된 정책도 목록에서 사라지지 않습니다.** 배지만 붙고 접힌 상태로 남으며, **왜 아닌지가 함께 적힙니다.** 요약을 잘못하는 것과 해당되는 정책을 걸러 없애는 것은 피해의 차원이 다릅니다 — 후자는 사용자가 신청 기회를 잃습니다.

코드가 확정한 `아님`에는 **정책이 요구하는 조건을 한글로 적고**(*"개인 상황 조건 불일치 (정책 대상: 근로자/직장인)"*) "해당하는 조건이 있다면 내 조건에 추가해 보세요" 링크를 붙였습니다. 다중선택 항목은 사용자가 고른 것만 담기므로, **잘못 걸러진 경우 사용자가 직접 되찾아올 수 있어야** 하기 때문입니다.

## 7. 기획서와 달라진 점

원 기획서는 **"AI 법안·정책 알리미"** 였습니다. 매일 새 공고와 관련 법안을 알림으로 받는 모델이었습니다.

- **뺀 것**
  1. **법안 추적**
  2. **알림 / 푸시 발송**
  3. **마감 임박 필터 · 신청기간 파싱**
  4. **비수도권 지역**
  5. **온통청년의 시군구 단위 판정**

- **뺀 이유**
  1. **법안은 "내가 해당되는가"라는 질문이 성립하지 않습니다.** 신청 대상이 아니기 때문입니다. 이 서비스의 유일한 판정 기준과 맞지 않아 뺐습니다
  2. **알림 모델 자체를 문제로 봤습니다.** 앞서 n8n으로 만든 알리미를 쓰면서 *"필요 없는 공고가 대부분"* 이었는데, 알림은 "새로 나온 것"을 기준으로 오지 받는 사람의 조건을 모르기 때문입니다. 그래서 **알림(push)을 조회·판정(pull)으로 뒤집었습니다**
  3. 두 출처 모두 신청기간 포맷이 제각각이고 빈 값이 많습니다(온통청년 49.8%). 잘못 파싱해 마감된 것으로 감추는 위험이 이득보다 큽니다. 원문 문자열 그대로 보여줍니다
  4. **특화 축이라 의도적으로 좁혔습니다** (아래)
  5. **실익이 없었습니다.** 서울 정책 478건 중 동대문구 코드를 가진 것이 467건 — **2%밖에 안 줄어듭니다.** 온통청년은 시도 단위까지만 씁니다

- **바꾼 것**
  - **알림 → 조회·판정** (위 2번)
  - **AI 분야 한정 → 다분야 개인 매칭.** 원 기획서는 AI 지원사업만 다뤘는데, 원래의 문제의식이 "분야를 좁히는 것"이 아니라 **"흩어진 정책을 내 조건으로 거르는 것"** 이었습니다. 그래서 분야는 넓히고 **개인 조건으로 좁혔습니다**

- **좁힌 것 — 수도권 특화. 실측으로 정했습니다**

  두 API를 전량 호출해 **어느 축이 실제로 걸러내는지 셌습니다.**

  | 축 | 온통청년 2,698건 | 정부24 10,964건 |
  |---|---|---|
  | 나이 (28세) | **4.0% 제거** ← 거의 못 거름 | 19.6% 제거 |
  | **지역 (서울)** | **82.3% 제거** | **68.3% 제거** (수도권 기준) |

  온통청년은 이미 전량이 청년정책이라 나이로는 4%밖에 못 거릅니다. **지역이 압도적이라 주축으로 삼았습니다.**

  좁혀서 **얻은 것**도 있습니다. 정부24 `소관기관명`이 `"서울특별시 동대문구"` 형태로 와서 **시·군·구 단위 판정이 가능**한데, 전국 261개 시군구는 부담이지만 수도권 3개 시도면 데이터에서 확정할 수 있습니다. *"동대문구 사는 사람에게 동대문구 정책을 보여준다"* — 시도 단위 서비스가 못 하는 세밀도입니다.

  **데이터는 전량 수집했습니다.** 수도권 특화는 화면 필터의 기본값이지 수집 범위가 아니라서, 지역을 넓히는 것은 필터 조건 변경입니다.

- **시간이 더 있었다면 넣었을 것**
  - **비수도권 확장** — 데이터가 이미 다 있어서 시군구 목록 도출만 하면 됩니다
  - **기업마당 등 3번째 출처** — `source` 컬럼 설계 덕에 행 추가로 끝납니다
  - **알림 재도입** — 단, 원래 방식이 아니라 **판정을 통과한 정책만** 보내는 형태로

## 8. 만들면서 가장 오래 막혔던 것

- **문제 : 13,662건을 "훑어볼 만한 규모"로 줄이는 일.** 목표는 200~400건이었습니다.

  대표 프로필(28세·서울·기본 분야 2개)로 1차 필터를 걸어보니 **906건**이 나왔습니다. 목표의 두 배가 넘습니다.

- **어떻게 해결했나 : 줄이는 데는 사실상 실패했고, 대신 목록이 왜 그 크기인지를 알아냈습니다.**

  **① 계획했던 두 조치가 다 안 통했습니다.**

  기획 단계에서 준비해둔 대응은 "시군구 선택을 유도하거나 기본 분야를 1개로 줄인다"였습니다. 재보니 시군구를 골라도 906 → 860(**-5%**), 분야를 `일자리` 하나로 줄여도 756건이었습니다. 걸러야 할 대상 대부분이 시군구 값이 없는 '전국' 정책으로 잡혀 있었기 때문입니다.

  **② 지역 판별이 생각보다 부정확한 걸 발견했습니다.**

  검증 기록에는 판별 실패가 0.9%로 적혀 있었는데, 전량으로 재보니 **15.4%(1,528건)** 였습니다. `공공기관` 100%, `지방공기업` 79.5%가 시도명으로 시작하지 않았습니다. 실패한 것은 전부 '전국'으로 처리되므로 **수도권 사용자 목록에 타 지역 정책이 섞이고 있었습니다.**

  기관명 안쪽까지 뒤져 지역명을 찾는 방식을 추가해 **15.4% → 11.3%** 로 낮췄습니다. 다만 **오탐이 나면 정책이 숨겨지므로**('전국'에서 '지역 전용'으로 바뀌면 다른 지역에서 안 보입니다) 규칙을 좁게 잡았습니다 — 정식 명칭만 쓰고(약칭까지 넓히면 `서울올림픽기념국민체육진흥공단` 같은 전국 기관이 서울 전용이 됩니다), 여러 시도에 겹치는 이름(`중구`·`동구` 등)은 제외했습니다. 매칭된 96개 기관을 **전수 확인해 오탐 0건**을 확인했습니다.

  **그런데 건수는 906 → 888, 18건밖에 안 줄었습니다.** 회수한 것들이 대부분 **실제로 서울 기관**이라 여전히 필터를 통과했기 때문입니다. 정확도는 올랐지만 규모 문제는 그대로였습니다.

  **③ 888건을 분해해보니 목표 자체가 도달 불가능이었습니다.**

  | 구분 | 건수 |
  |---|---|
  | **전국 정책 (중앙행정기관 등)** | **502** |
  | 전국 (판별 실패 잔여) | 290 |
  | 서울 시군구 | 53 |
  | 서울 시도전역 | 43 |

  **502건은 진짜 전국 정책이라 서울 거주자에게 실제로 해당됩니다.** 지역 판별이 완벽해져도 안 줄어듭니다. 즉 지역 축으로는 하한이 약 500건이고, **200~400은 측정 전에 세운 도달 불가능한 수치**였습니다.

  **④ 지역이 아닌 다른 축을 찾았습니다.**

  수집만 해두고 쓰지 않던 `사용자구분` 필드를 세어보니, 888건 중 **`법인/시설/단체` 전용이 271건(30.5%)** 이었습니다. **개인이 신청 자체를 할 수 없는 공고**가 목록의 3분의 1이었던 겁니다.

  이건 이 서비스를 만든 계기였던 불만 — *"지원도 못하는 공고가 보인다"* — 에 정확히 해당하는 공고입니다. 판정 게이트와 목록 필터 양쪽에 넣어 **888 → 617건**이 됐고, 걸린 정책에는 *"법인/시설/단체 대상, 개인은 신청할 수 없습니다"* 라는 이유가 붙습니다. 단, **소상공인은 일부러 남겼습니다** — 이 프로젝트의 출발점이 AI 지원사업이고 그 대다수가 사업자 대상이라 빼면 핵심 용도가 사라집니다.

- **배운 것**

  **"목표 수치가 안 나온다"를 목표 쪽 문제로 의심하는 데 가장 오래 걸렸습니다.** 200~400이라는 숫자는 데이터를 재기 전에 정한 것인데, 저는 그게 맞다고 전제하고 계속 필터를 깎았습니다. 구성을 분해해 *"이 중 502건은 어떤 필터로도 못 줄인다"* 를 확인하고 나서야 방향이 바뀌었고, 그제서야 지역이 아닌 축(`사용자구분`)이 보였습니다.

  같은 종류의 실수가 이 프로젝트에서 반복됐습니다. **표본으로 잰 수치가 전량에서 깨진 것이 네 번**입니다 — 지역 매핑 방식, "빈 값 = 전국"이라는 가정, `선정기준` 채움률(99.8% → 실제 9.6%), 지역 판별 실패율(0.9% → 15.4%). 매번 원인이 같았습니다. **표본이 한쪽에 쏠려 있었는데 그걸 전체라고 믿었습니다.** 이후로는 비율을 표본이 아니라 서버가 주는 전체 건수로 확인했습니다.
